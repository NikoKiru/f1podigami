## Automated data updates (`update.yml`)

Keeps the site fresh with no manual step, running the same pipeline as a local `python src/update.py` + push:

- A cheap **`check` job** runs `src/check_update_due.py` **every 15 min** (`cron: 2,17,32,47 * * * *`; offset off the hour to dodge GitHub's top-of-hour load, which often drops scheduled runs; no secret, and no network except the calendar lookup below) and proceeds only when a pending session is newer than the data: a race newer than `podigami.json`'s `asOf`, the next race's qualifying not yet covered by `postQuali`, or that race's official starting grid not yet in `data/starting_grids.json`. The guard **arms 3 h before each session's scheduled start** (`ARM_BEFORE`), so a run is already waiting when results appear. Between seasons it also compares the API's calendar with the committed one (see `.claude/rules/season-rollover.md`). A weekly run (`0 7 * * 1`) is meant to force an unconditional `--full` reconciliation, but that single slot usually doesn't land: 1 of the 10 Mondays from 2026-08-24 to 2026-10-26. Don't rely on it; `workflow_dispatch` takes `mode` (auto/full), `force`, and `wait` (hold the runner like a scheduled run — successor runs set it).
- When due, the **`update` job first waits for the results to exist** (see below), then runs `update.py`, opens/updates a single `auto/update-data` PR with **squash auto-merge**, and only then validates + tests (so a bad run surfaces as a visible red PR rather than a silently-skipped step). Once the full required checks pass it merges → `deploy.yml` ships it. One race ⇒ one PR (the guard stops once `asOf` advances on merge); re-running is idempotent (no churn).
- A **`watchdog` job** runs on every tick regardless of the guard, and is the only job *not* pinned to `main` (it reads no data, and its script must come from the same ref as the workflow file). It asks the API for the open `auto/update-data` PR and, if that PR has existed longer than `check_stalled_data_pr.STALL_AFTER` (**45 min**) without merging, reports why — failing required check, merge conflict, auto-merge not armed — into the same deduplicated `auto-update-failure` issue `notify-failure` uses. A *green* run whose PR sits `BLOCKED` was the last silent path (#229).
- A **`Detect podium revisions`** step (`src/check_revisions.py`) compares every podium already on `main` with the refreshed data. A change — Jolpica editing a settled race — retitles the data PR (`Update race data … · Podium revised: 2026 R6 Monaco Grand Prix — Hadjar → Gasly`) and opens one issue per revision, or a single summary issue when more than `MAX_ISSUES` (5) revise at once (a mid-season renumbering or a `--full` run). Dedup is against **open** `podium-revised` issues only — closing one re-arms detection, so a repeat flip-flop after that still notifies. Close a `podium-revised` issue only after its data PR has merged: closing it while the PR is still unmerged makes the next run open an identical one. It never blocks the auto-merge: the retitle (via `DATA_PUSH_TOKEN`, the REST API rather than `gh pr edit` — that command also queries projects/labels/milestones a fine-grained PAT may not be allowed to read) happens only *after* `gh pr merge --auto` has already armed, and the PR label (via `GITHUB_TOKEN`, also REST rather than `gh pr edit`) is applied only after the issues are created. Both the retitle and the label are non-fatal (`|| echo "::warning::..."`); issue creation stays loud, since a revision alert failing to notify is the one failure mode that must surface. Issues/labels use `GITHUB_TOKEN` because `DATA_PUSH_TOKEN` has no Issues permission.

## The cron is a handful of runs a day, not every 15 min — don't design around the schedule

GitHub honours only a fraction of the requested slots. Measured on race Sunday 2026-07-19: **13 scheduled runs against 76 expected (~17%)**, landing at arbitrary minutes (not `:02/:17/:32/:47`), with multi-hour overnight gaps, and one slot additionally queued **41 min** before executing. This is normal Actions throttling for scheduled workflows; **making the cron denser does not help** — the extra slots are dropped too.

It got worse: from **2026-08-27** GitHub delivered only **~6–7 of 96 slots a day** (gaps: median 39 min, p90 4.2 h, max 11.9 h — `docs/research/2026-09-08-live-data-latency.md`). That regime is why the guard now arms *before* sessions and why a timed-out watch hands over to a successor run rather than waiting for the next slot.

The consequence that actually hurts: the Jolpica API often has not published a just-finished race when the run fetches. Previously that meant the run produced a PR with no new race (`asOf` unchanged), and the retry had to wait for the *next surviving slot* — **a full hour**. At the 2026 Belgian GP that put the result on the site ~100 min after the flag (fetched 15:32Z with nothing upstream → PR #204 carried no race → only #205 at 16:23Z did).

**Fix (#206, extended #323): wait in-run rather than retry across runs.** `src/wait_for_results.py` polls every 3 min for up to **5 h** until the pending round appears — `/{season}/last/results.json` for a race, the last row of `/{season}/qualifying.json` for qualifying. Notes:
- It polls **aggregate** feeds on purpose — the round-indexed endpoints lag for hours (see #178 below).
- The guard arms **3 h before** each race and qualifying session (`check_update_due.ARM_BEFORE`): a run is already waiting when the data lands in **93% of races / 91% of qualifying sessions**, replaying 14 days of the post-2026-08-27 scheduler — measured against **OpenF1's** publish time (`docs/superpowers/specs/2026-09-10-openf1-fast-lane-design.md` section 4), assuming OpenF1 has the result ~40 min after the flag. The fast lane now does use OpenF1, and at the 2026 Spanish GP it came later than that (about three hours after the start), so a run that armed right at the start of the 3 h window can time out (start + 2 h) before OpenF1 has the result; the successor hand-over then carries the watch on, exactly as it does for Jolpica. Against Jolpica's own, later and more variable publish, the hand-over chain below keeps a watch alive across the gap, so coverage is at least as high. Arming early costs only idle runner time.
- A timeout is **not** a failure: the watcher reports `published=false` and the job **hands over to a successor run immediately, skipping the pipeline** (`gh workflow run update.yml -f mode=auto -f wait=true`, built-in token, `actions: write` scoped to just the `update` job) while the session is < 12 h past its scheduled start (`SUCCESSOR_WINDOW`) — so a later link in the chain runs the pipeline once the round actually shows up, instead of two pipelines racing Jolpica's hourly rate limit minutes apart. Only after that window elapses does the run fall through and run the pipeline anyway (idempotent), as a fallback. A run whose watcher finds nothing pending at all reports `published=none`, which also skips the pipeline — there being nothing to do, running `update.py` again right after the hold would just repeat a no-op.
- The `update` job's first step waits (≤ 15 min) for any open `auto/update-data` PR to merge, so a successor never computes on a `main` that is about to change; the pipeline step then re-syncs to `origin/main` first, so a PR that merges during a long watch is included.
- It runs on **scheduled events and successor dispatches** (`wait=true`), not for `mode=full` or a plain human dispatch, which stays snappy.
- The `update` job carries `timeout-minutes: 345` (15 min PR wait + 5 h watcher + ~20 min pipeline, under GitHub's 6 h cap); the pipeline step itself (`Fetch latest data and rebuild site`) additionally carries `timeout-minutes: ${{ needs.check.outputs.mode == 'full' && 60 || 25 }}` — full reconciliations take ~24 min and never run the watcher, so they get 60; a normal run after a 5 h watch keeps 25 so the job stays under 345 min — so a runaway fetch fails loudly instead of the whole job being cancelled silently at 345 min.
- Trigger on demand: `gh workflow run update.yml -f mode=auto -f force=true` (or `-f mode=full`; add `-f wait=true` to hold the runner and poll). **On a race weekend, always add `-f wait=true`** — a plain dispatch that lands the pending slot acts immediately and skips the watcher, ending the hand-over chain (no successor is dispatched from it), and a dispatch without `wait=true` still queues behind the `update-data` concurrency group, which can hold for the chain's ~5¾ h — a dispatch waiting in that queue can itself be replaced by a successor before it ever runs (`cancel-in-progress: false` never cancels a run that has already started).
- The `update-data` concurrency group now holds for hours during a chain, not the usual ~20 min: the `watchdog` job (part of the same workflow run as the held `update` job) only gets a fresh report once per link, so during a chain its cadence degrades from ~15 min to however far apart the links land; and a successor dispatched while a pending weekly `--full` run is still queued behind the group cancels that queued run — accepted, since `--full` reconciles again the following Monday.
